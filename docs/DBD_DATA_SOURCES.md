# DBD 10.2.2: исследование источников и состояние подключения

Дата проверки: **23 октября 2026**. Репозиторий: [psenicynarsenij-ship-it/DBD-soft-project](https://github.com/psenicynarsenij-ship-it/DBD-soft-project). Основа — слитый PR #2 и существующие RuntimeDataProvider, Frame, Camera, JSON/Replay и renderer.

**Подходящий документированный источник полного пространственного потока не найден в доступных для проверки материалах. Реальное подключение к DBD 10.2.2 не реализовано и не проверено.** `DBDDataSource` не добавлен: класс без подтверждённого транспорта и схемы лишь имитировал бы интеграцию. Demo, JSON и Replay сохранены; новый статус явно сообщает `DBD 10.2.2: NOT CONNECTED`.

Это ограниченный результат исследования, а не доказательство отсутствия любых закрытых, партнёрских или новых интерфейсов. Актуальные сайты BHVR, Steamworks и Overwolf из этой среды не прочитаны: прокси отклонил HTTPS CONNECT с 403. Ответ прокси нельзя считать ответом сайта, отсутствием API или отказом разработчика в доступе. Установленный клиент или подтверждённая сессия для проверки не предоставлены, сборка/сессия игры не наблюдалась; `10.2.2` — запрошенная метка, а не автоматически обнаруженная версия клиента.

## Недостающие данные для полноценного ESP

Нужен документированный и поддерживаемый производителем поток для конкретной версии клиента, с условиями доступа и воспроизводимыми образцами. Его минимальные поля:

1. Стабильные ID, роли/категории и мировые координаты **всех требуемых** survivors и killer; для рамок — верхняя точка/документированный bounding volume. Данные только о локальном игроке не заменяют остальных участников.
2. ID/типы и фактические координаты generators, hooks и exit gates текущей сессии. Одного справочника объектов или имени карты недостаточно.
3. Позиция камеры и view-projection 4×4; либо документированные pose/rotation, тип проекции, FOV, aspect, near/far для её корректного построения. Дополнительно viewport/letterboxing, система осей, единицы, порядок матриц и clip-depth convention.
4. Нормализованный world-space look vector killer, либо документированные yaw/pitch/transform для его вычисления. Направление движения не подменяет направление взгляда.
5. Границы сессий, последовательность/время снимков, правила появления/исчезновения объектов, валидность и частота обновления; связь всех полей с одним согласованным кадром.
6. Подтверждённая совместимость с 10.2.2, способ аутентификации и технический контракт, позволяющий использовать именно перечисленные данные. Наличие endpoint или публичного стороннего клиента не подтверждает это автоматически.

При появлении такого контракта DBDDataSource должен реализовать существующий IFrameSource, перевести данные в Frame (метры, +Y up, left-handed, row-major VP × column vector, clip-depth 0..w), пройти ValidateFrame и проверку на подтверждённой реальной сессии. Успешный JSON parse, активный LIVE транспорт или проигрывание записи не являются такой проверкой. До этого отсутствующие значения не заполняются демонстрационными и нулевыми координатами.

## Что изменено в программе

- Добавлена независимая от графики модель DbdConnectionStatus с честным состоянием **NOT CONNECTED**, версия — только target label.
- В существующий диагностический HUD добавлена одна строка статуса игры. Вкладки, визуальные настройки, FOV, стрелка/сектор, категории, hotkeys и click-through не переделывались.
- JSON `source="VERIFIED LIVE DBD"`, `connected=true` или `dbd.verified=true` не могут аутентифицировать игру: runtime сохраняет маркировку непроверенного транспорта. Demo fallback остаётся явно синтетическим.
- `frame_tool dbd-status` выводит JSON о **возможностях этого binary**, не опрашивает запущенный overlay/игру и возвращает ожидаемый exit code **3** (unavailable). Это отдельное состояние от успешной передачи тестовых кадров.
- Конфигурация/Frame schema сохранены. Источники `demo`, `json`, `replay` работают; источник `dbd` не добавлен как фиктивный режим и отвергается. Все реальные смещения остались неизвестными.

## Отдельные результаты

**Что действительно работает с DBD 10.2.2:** подтверждённой интеграции с реальной игрой нет; ни одно пространственное поле из живой сессии не получено и не проверено.

**Что работает с тестовыми/внешними непроверенными данными:** существующий ESP renderer, camera FOV Demo, направление/сектор killer, JSON, snapshots, reconnect, запись/Replay, диагностика и настройки. Локальный JSON может содержать пользовательские данные, но их происхождение программа не подтверждает.

**Что необходимо для полного ESP:** поддерживаемый пространственный источник с полями выше и проверка на реальной сессии. Здесь нет подтверждённого источника; недостающий upstream нельзя заменить настройкой offsets.json.

**Какие проверки выполнены:** CTest, негативные проверки поддельных connection/provenance полей, потеря файла/fallback и CLI exit code; Windows x64 Release кросс-сборка. Точные результаты и ограничения графического запуска/MSVC приведены в [VALIDATION.md](../VALIDATION.md).
